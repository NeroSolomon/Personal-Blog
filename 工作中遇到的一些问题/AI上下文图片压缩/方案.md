会话图片容量优化方案
1. 问题背景
现象
Game策划用户在 Cowork 会话中频繁粘贴图片（UI截图、配表截图、概念原画等），导致会话存储体积快速膨胀，超过 AI 的 100MB 请求体大小限制，触发 413 RequestEntityTooLargeFromAI 错误，会话不可用。

数据表现
指标	值	说明
AI 请求体上限	100MB (104,857,600 bytes)	硬限制
用户实际请求体	~115MB (121,245,203 bytes)	超限约 15%
token 上下文使用率	22.6% (936k / 968k)	远未饱和
对话轮数	64 轮	正常使用量
核心矛盾：图片以 base64 存储在会话中，体积巨大（单张 2-5MB）但 token 占用低，导致存储先于上下文爆满。

用户场景
game策划的典型工作流：贴 UI 截图 → 讨论 → 贴配表截图 → 讨论 → 贴概念图 → 讨论……一个会话贴十几张图片是常态。

2. 方案概述
采用分层存储 + 智能淘汰策略：

上传图片时，异步生成文字描述作为备份（Layer 2）
会话体积接近上限时，按优先级将早期图片的 base64 替换为文字描述
S3 原图链接始终保留，支持按需重新加载
前端无感知，照常展示图片；用户无提示，底层静默处理
3. 存储分层设计
每张用户上传的图片维护三层数据：

┌───────────────────────────────────────────────────────┐
│  Layer 1: 原图 base64          ~2-5MB/张              │
│  ├─ 完整图片数据，供模型直接理解                        │
│  └─ 体积大，是容量膨胀的主要来源                        │
│                                                        │
│  Layer 2: 结构化文字描述        ~1-3KB/张              │
│  ├─ OCR 提取的文字内容                                 │
│  ├─ Vision 模型生成的语义描述                           │
│  └─ 图片分类标签                                       │
│                                                        │
│  Layer 3: S3 URL               ~200B/张               │
│  ├─ 原图的 S3 存储链接（有效期 30 天）                  │
│  └─ 始终保留，不参与淘汰                               │
└───────────────────────────────────────────────────────┘

淘汰方向：Layer 1 → Layer 2（Layer 3 永久保留）
4. 详细流程
4.1 图片上传时（预处理）
用户粘贴图片
  │
  ├─ 同步：存储原图 base64 到会话 (Layer 1)
  │        正常响应用户，不阻塞
  │
  └─ 异步：生成结构化文字描述 (Layer 2)
           ├─ 调用 gemini-3.1-flash-preview 生成描述
           │   ├─ OCR 文字提取（配表、报错截图等）
           │   ├─ 语义描述（UI布局、美术风格、空间关系等）
           │   └─ 图片分类标签（见下方分类表）
           └─ 将描述结果关联存储到该图片的元数据中
异步描述生成的 prompt 参考：

请对这张图片生成结构化描述，包含：
1. 图片类型分类（screenshot/spreadsheet/concept_art/UI_design/map_layout/error_log/other）
2. OCR 文字提取（如有可读文字）
3. 视觉内容描述（布局、元素、颜色、风格等关键信息）
4. 关键数据提取（如有数值、表格数据）

输出 JSON 格式：
{
  "type": "screenshot|spreadsheet|concept_art|UI_design|map_layout|error_log|other",
  "ocr_text": "提取的文字内容",
  "description": "视觉内容的语义描述",
  "key_data": "关键数值/表格数据（如有）"
}
模型选择：gemini-3.1-flash-lite-preview，成本低、速度快，描述质量足够用于上下文回忆。

4.2 容量淘汰触发
触发阈值
阶段	阈值	动作
正常	< 70MB	无操作
软淘汰	70MB ~ 90MB	按优先级淘汰"高可替代"图片
强制淘汰	> 90MB	按时间顺序淘汰所有超出部分的图片
阈值基于 100MB 上限设计，预留 10MB 缓冲给当轮新增内容。

淘汰优先级
按「文字替代效果」从高到低排序，优先淘汰文字替代效果好的图片：

优先级	图片类型	文字替代效果	说明
P0（最先淘汰）	spreadsheet	⭐⭐⭐⭐⭐	配表截图，OCR 几乎无损还原
P0	error_log	⭐⭐⭐⭐⭐	报错截图，文字完美还原
P1	screenshot	⭐⭐⭐⭐	通用截图，OCR+描述覆盖大部分信息
P2	UI_design	⭐⭐⭐	UI 设计图，布局和层次关系有损失
P3	map_layout	⭐⭐	关卡/地图布局，空间关系难以文字化
P4（最后淘汰）	concept_art	⭐	概念原画，美术风格/配色/氛围大量丢失
淘汰排序规则：同优先级内按时间从早到晚淘汰。

4.3 淘汰执行
将目标图片的 Layer 1（base64）替换为 Layer 2（文字描述），格式如下：

[此处原为用户上传的图片，已转为文字描述]
图片类型：{type}
图片内容：{description}
文字提取：{ocr_text}
关键数据：{key_data}
原图链接：{s3_url}
4.4 按需重新加载（可选，后续迭代）
当用户在对话中明确引用已淘汰的图片时（如"帮我看看前面那张原画"），可以：

识别用户意图指向已淘汰的图片
通过 S3 URL 重新拉取原图
临时注入到当前请求的上下文中（不持久化回会话存储）
此功能为增强体验，可作为后续迭代，MVP 阶段不做。

5. 前端处理
前端无需改动核心逻辑，底层静默处理：

前端消息流中图片仍然按原样展示（使用 S3 URL 渲染）
淘汰操作仅影响发送给模型的会话数据，不影响前端消息展示
用户看到的历史消息中图片始终存在，不会出现图片消失的情况
6. 数据结构变更
图片消息元数据扩展
interface ImageMeta {
  // 现有字段
  s3_url: string;           // S3 存储链接
  base64?: string;          // 原图 base64（淘汰后为 null）
  
  // 新增字段
  text_backup?: {           // 文字描述备份
    type: 'screenshot' | 'spreadsheet' | 'concept_art' | 'UI_design' | 'map_layout' | 'error_log' | 'other';
    ocr_text: string;       // OCR 提取文字
    description: string;    // 语义描述
    key_data?: string;      // 关键数据
    generated_at: number;   // 生成时间戳
    model: string;          // 生成模型（如 gemini-3.1-flash-lite-preview）
  };
  evicted: boolean;         // 是否已被淘汰（base64 已移除）
  evicted_at?: number;      // 淘汰时间戳
  original_size: number;    // 原始 base64 大小（bytes），用于容量计算
}
7. 容量计算
发送前容量检查
def calculate_session_size(messages):
    """计算会话序列化后的预估体积"""
    total_size = 0
    for msg in messages:
        if msg.has_image:
            if not msg.image_meta.evicted:
                total_size += msg.image_meta.original_size  # base64 体积
            else:
                total_size += len(msg.image_meta.text_backup.to_json())  # 文字描述体积
        total_size += len(msg.text_content.encode('utf-8'))  # 文字内容体积
    return total_size


def evict_if_needed(messages, limit=100 * 1024 * 1024):
    """按优先级淘汰图片直到体积低于阈值"""
    current_size = calculate_session_size(messages)
    if current_size <= limit * 0.7:  # 70% 以下不触发
        return
    
    # 收集所有未淘汰的图片，按淘汰优先级排序
    candidates = get_eviction_candidates(messages)  # 按 type 优先级 + 时间排序
    
    for candidate in candidates:
        if current_size <= limit * 0.7:
            break
        saved = candidate.image_meta.original_size - len(candidate.text_backup_json)
        candidate.evict()  # base64 → text_backup
        current_size -= saved

2	图片上传时异步生成文字描述	P0	1.5d	接入 gemini-3.1-flash-preview，异步任务队列
3	会话容量计算模块	P0	1d	准确计算序列化后体积
4	淘汰优先级排序逻辑	P0	1d	按图片类型 + 时间排序

7	监控与告警	P1	0.5d	淘汰触发频率、描述生成成功率等

9. 注意事项
S3 链接有效期 30 天：对于活跃会话足够覆盖；超过 30 天的会话即使图片链接失效，文字描述仍可用
发送时已有压缩：当前图片在发送时已经做了压缩处理，本方案不改动压缩逻辑
100MB 上限暂不调整：本方案在 100MB 限制下即可解决问题；后续如有需要可评估调整至 150MB
异步描述生成失败兜底：如果 flash 模型调用失败，text_backup 为空，淘汰时降级为仅保留 S3 URL + 基础信息（文件名、上传时间、图片尺寸）
存量会话处理：已存在的会话中图片没有 text_backup，淘汰时需要同步生成描述（此时会有一次性延迟），或降级为仅 URL 兜底

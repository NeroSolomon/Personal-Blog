# 什么是Transformer 架构原理（Attention 机制）

Transformer 是现代大语言模型的基石。下面我从**核心思想**到**具体计算**逐层拆解。

---

## 一、为什么需要 Transformer？

在 Transformer（2017 年《Attention is All You Need》）出现之前，主流是 **RNN/LSTM**，它们有两个致命问题：

| 问题 | RNN/LSTM | Transformer |
|------|----------|-------------|
| **并行计算** | 必须按时序逐个处理，无法并行 | 全序列并行计算 |
| **长距离依赖** | 距离越远信息衰减越严重 | 任意两个 token 直接建立联系 |

**核心突破**：抛弃循环结构，完全依靠 **Attention 机制**来建模序列关系。

---

## 二、整体架构

Transformer 由 **Encoder（编码器）** 和 **Decoder（解码器）** 组成：

```
输入 → [Embedding + 位置编码] → Encoder×N → Decoder×N → 输出
```

> **注意**：现在的 GPT 系列是 **Decoder-only** 架构，BERT 是 **Encoder-only**，理解 Attention 是理解两者的关键。

---

## 三、核心：Self-Attention（自注意力）

### 1. 直觉理解

一句话："**The animal didn't cross the street because it was too tired**"

这里的 `it` 指代什么？是 `animal` 还是 `street`？

Attention 机制让 `it` 能够"**关注**"到句子里其他词，并计算出它和 `animal` 的关联度最高。

### 2. 三个核心矩阵：Q、K、V

每个输入 token 会通过三个不同的权重矩阵，生成三个向量：

| 向量 | 名称 | 类比 |
|------|------|------|
| **Q** (Query) | 查询 | 我要找什么？ |
| **K** (Key) | 键 | 我能提供什么信息？ |
| **V** (Value) | 值 | 我实际的内容是什么？ |

**类比图书馆**：
- 你带着一个问题（**Query**）去检索
- 每本书有标签（**Key**）
- 匹配到后取出书的内容（**Value**）

### 3. 核心计算公式

$$
\text{Attention}(Q, K, V) = \text{softmax}\left(\frac{QK^T}{\sqrt{d_k}}\right)V
$$

**分步拆解**：

```
Step 1: 计算相似度    scores = Q · Kᵀ
        （每个 token 的 Query 和所有 token 的 Key 做点积）

Step 2: 缩放          scores / √d_k
        （防止点积过大导致 softmax 梯度消失）

Step 3: 归一化        weights = softmax(scores)
        （得到 0~1 的注意力权重，总和为 1）

Step 4: 加权求和      output = weights · V
        （用权重对 Value 加权，得到最终输出）
```

### 4. 为什么要除以 √d_k？

当维度 `d_k` 很大时，`Q·Kᵀ` 的结果会很大，导致 softmax 进入**梯度平缓区**（饱和区），训练时梯度几乎为 0。除以 `√d_k` 起到**归一化缩放**作用，稳定训练。

---

## 四、Multi-Head Attention（多头注意力）

### 1. 为什么需要"多头"？

单个 Attention 只能捕捉**一种**关系模式。多头就像**多个专家从不同角度看问题**：

- 头 1 可能关注**语法关系**
- 头 2 可能关注**指代关系**
- 头 3 可能关注**语义关联**

### 2. 计算流程

```
输入 → 拆分成 h 个头 → 每个头独立做 Attention → 拼接 → 线性变换
```

$$
\text{MultiHead}(Q,K,V) = \text{Concat}(\text{head}_1, ..., \text{head}_h)W^O
$$

比如维度 512，分成 8 个头，每个头处理 64 维，最后拼接回 512 维。

---

## 五、其他关键组件

### 1. 位置编码（Positional Encoding）

Attention 本身**没有位置概念**（打乱词序结果一样），所以要注入位置信息：

$$
PE_{(pos, 2i)} = \sin\left(\frac{pos}{10000^{2i/d}}\right), \quad PE_{(pos, 2i+1)} = \cos\left(\frac{pos}{10000^{2i/d}}\right)
$$

> 现代模型多用 **RoPE（旋转位置编码）**，能更好地处理长序列外推。

### 2. 前馈网络（FFN）

每个 Attention 层后接一个两层的全连接网络，做非线性变换：

$$
\text{FFN}(x) = \max(0, xW_1 + b_1)W_2 + b_2
$$

### 3. 残差连接 + 层归一化

```
output = LayerNorm(x + Attention(x))
```

- **残差连接**：缓解深层网络梯度消失
- **LayerNorm**：稳定训练

---

## 六、单个 Transformer Block 全景图

```
        输入 x
          │
    ┌─────┴─────┐
    │  Multi-Head │
    │  Attention  │
    └─────┬─────┘
          │
     [+ 残差] → LayerNorm
          │
    ┌─────┴─────┐
    │    FFN     │
    └─────┬─────┘
          │
     [+ 残差] → LayerNorm
          │
        输出
```

---

## 七、面试常见追问

作为面试官，我通常会顺着这个话题继续追问：

1. **Self-Attention 的时间复杂度是多少？** → `O(n²·d)`，序列长度平方级，这也是长文本的瓶颈
2. **Decoder 的 Attention 有什么不同？** → 使用 **Masked Attention**，防止看到未来 token（因果掩码）
3. **如何优化 Attention 的效率？** → Flash Attention、稀疏 Attention、KV Cache
4. **Encoder 和 Decoder 的 Attention 有几种？** → Self-Attention、Masked Self-Attention、Cross-Attention

---

## 八、一句话总结

> **Transformer 的核心是用 Attention 机制让序列中每个位置都能直接、并行地关注到所有其他位置，通过 Q/K/V 计算关联权重来动态聚合信息，从而高效建模长距离依赖。**

# LLM 核心参数详解：Token、上下文窗口与采样策略

这些是理解大模型行为和调优的基础概念，也是面试中的高频考点。

---

## 一、Token（词元）

### 1. 什么是 Token？

Token 是模型处理文本的**最小单位**。模型不认识"字符"或"单词"，只认识 Token。

**分词示例**：

```
"Hello, world!"  →  ["Hello", ",", " world", "!"]   （4 个 token）
"人工智能"        →  ["人", "工", "智", "能"]          （中文常按字切分）
"ChatGPT"        →  ["Chat", "GPT"]                  （可能被拆开）
```

### 2. Token 的经验换算

| 语言 | 换算规律 |
|------|---------|
| 英文 | 1 token ≈ 0.75 个单词 ≈ 4 个字符 |
| 中文 | 1 个汉字 ≈ 1~2 token |

> **面试点**：为什么中文更"费" token？因为主流分词器（BPE）基于英文语料训练，中文字符编码效率较低。

### 3. 为什么 Token 很重要？

- **计费单位**：API 按 Token 收费（输入 + 输出）
- **性能瓶颈**：Attention 复杂度是 `O(n²)`，Token 越多越慢越贵
- **上下文限制**：直接决定能塞多少内容

---

## 二、上下文窗口（Context Window）

### 1. 定义

模型在**一次推理**中能"看到"的最大 Token 数量，包括 **输入 + 输出**。

```
上下文窗口 = System Prompt + 历史对话 + 当前输入 + 模型输出
```

### 2. 常见模型的窗口大小

| 模型 | 上下文窗口 |
|------|-----------|
| GPT-3.5 | 4K / 16K |
| GPT-4 Turbo | 128K |
| Claude 3.5 | 200K |
| Gemini 1.5 Pro | 1M~2M |

### 3. 关键认知（面试易错点）

- **窗口 ≠ 记忆**：模型本身**无状态**，多轮对话是靠每次把历史全部重新传入实现的
- **"Lost in the Middle"现象**：长上下文中，模型对**中间部分**的信息利用率较低，开头和结尾记得更牢
- **窗口越大 ≠ 效果越好**：塞太多无关内容反而会稀释关键信息、增加成本

> **工程实践**：这正是需要 RAG、上下文压缩、滑动窗口等技术的原因。

---

## 三、采样参数：控制生成的"随机性"

模型每一步预测的是**下一个 Token 的概率分布**。采样参数决定如何从这个分布中"选词"。

### 核心机制

```
模型输出 → logits → softmax → 概率分布 → 采样策略 → 选出 token
```

---

### 1. Temperature（温度）

控制概率分布的**平滑程度**，即随机性的强弱。

**数学原理**：温度作用在 softmax 之前

$$
P(x_i) = \frac{e^{z_i / T}}{\sum_j e^{z_j / T}}
$$

| 温度值 | 效果 | 分布变化 | 适用场景 |
|--------|------|---------|---------|
| **T → 0** | 确定性最强 | 尖锐，几乎总选最高概率 | 代码、数学、事实问答 |
| **T = 1** | 原始分布 | 保持模型原始概率 | 通用对话 |
| **T > 1** | 随机性强 | 平缓，低概率词也可能被选 | 创意写作、头脑风暴 |

**直觉图示**：

```
低温 (T=0.2)          高温 (T=1.5)
█                     █
█                     █ █ █
█ █                   █ █ █ █ █
"确定，保守"           "发散，多样"
```

---

### 2. Top-p（核采样 / Nucleus Sampling）

**动态**地从**累积概率达到 p** 的最小 Token 集合中采样。

**工作方式**：

```
假设 top-p = 0.9，候选词概率排序：
苹果 0.5  ┐
香蕉 0.3  ├─ 累积 0.9，进入候选池 ✓
橙子 0.1  ┘
葡萄 0.05    ← 被截断 ✗
其他 ...     ← 被截断 ✗

→ 只在 {苹果, 香蕉, 橙子} 中按概率采样
```

| Top-p 值 | 效果 |
|----------|------|
| **0.1** | 只考虑最核心的几个词，保守 |
| **0.9** | 覆盖大部分合理选项，平衡 |
| **1.0** | 考虑全部词汇 |

> **核心优势**：候选池大小是**动态**的——分布集中时池子小，分布分散时池子大，比固定数量更灵活。

---

### 3. Top-k

只从概率**最高的 k 个** Token 中采样（固定数量）。

```
top-k = 3  →  只保留概率前 3 的词，其余归零后重新归一化
```

**Top-k vs Top-p 对比**：

| 维度 | Top-k | Top-p |
|------|-------|-------|
| 候选池 | 固定数量 | 动态（按累积概率） |
| 缺点 | 分布尖锐时冗余，平缓时可能截断合理词 | 相对更智能 |

---

### 4. 其他常用参数

| 参数 | 作用 |
|------|------|
| **frequency_penalty** | 惩罚已出现词的**频率**，减少重复啰嗦 |
| **presence_penalty** | 惩罚已出现的词（不看次数），鼓励谈新话题 |
| **max_tokens** | 限制输出的最大长度 |
| **stop** | 遇到指定字符串就停止生成 |

---

## 四、参数组合实战建议

| 应用场景 | Temperature | Top-p | 说明 |
|---------|-------------|-------|------|
| **代码生成** | 0 ~ 0.2 | 1.0 | 要确定、准确 |
| **事实问答** | 0 ~ 0.3 | 0.9 | 减少幻觉 |
| **通用对话** | 0.7 | 0.9 | 平衡 |
| **创意写作** | 0.9 ~ 1.2 | 0.95 | 要多样、发散 |

> **实践经验**：通常**只调其中一个**（Temperature 或 Top-p），不建议同时大幅调整两者，否则效果难以预测。

---

## 五、面试常见追问

作为面试官，我会这样深挖：

1. **Temperature=0 一定完全确定吗？**
   → 理论上是，但实际因浮点运算、并行计算等，可能有微小不确定性

2. **Top-p 和 Temperature 同时设置，谁先生效？**
   → Temperature 先调整分布 → 再用 Top-p 截断 → 最后采样

3. **为什么 RAG 场景推荐低温度？**
   → 已有检索到的准确上下文，要的是"忠实复述"而非"自由发挥"，降低幻觉

4. **如何解决输出重复问题？**
   → 调 `frequency_penalty` / `presence_penalty`，或检查是否温度过低

---

## 六、一句话总结

> **Token 是模型处理的基本单位，上下文窗口决定"能看多少"，而 Temperature / Top-p / Top-k 等采样参数共同控制生成的"随机性与创造力"——低温保守求准确，高温发散求多样。**

# 模型能力边界与幻觉（Hallucination）的成因

这是 Agent 开发中**最核心的认知基础**——不理解模型为什么会"胡说八道"，就无法设计出可靠的 Agent 系统。下面我系统性地讲解。

---

## 一、什么是幻觉（Hallucination）

模型生成了**看似合理、语法通顺，但事实错误或无中生有**的内容。

### 两种典型分类

| 类型 | 说明 | 例子 |
|------|------|------|
| **事实性幻觉** | 与真实世界事实矛盾 | 说"爱因斯坦获得过两次诺贝尔奖" |
| **忠实性幻觉** | 与用户提供的上下文/指令矛盾 | 让它总结文档A，它却编造了文档里没有的内容 |

---

## 二、幻觉的根本成因

### 1. 模型的本质是"概率预测"，而非"事实检索"

这是最根本的原因。

```
LLM 做的事：给定前文，预测下一个最可能的 token
LLM 不做的事：查证这句话是否为真
```

模型追求的是**语言的流畅性和统计合理性**，而不是**事实正确性**。当"听起来对"和"事实上对"冲突时，模型倾向于前者。

> 💡 类比：一个能言善辩但从不查资料的人，遇到不知道的问题会"顺着语感编下去"。

---

### 2. 训练数据的固有缺陷

- **数据本身有错误**：互联网语料包含大量错误信息、过时内容、矛盾说法
- **数据分布不均**：冷门知识样本少，模型"记不牢"，容易靠猜
- **知识截止（Knowledge Cutoff）**：训练数据有时间边界，之后发生的事一概不知

---

### 3. 训练目标的错位（关键机制）

#### 预训练阶段
目标是最大化下一个 token 的预测概率 → **鼓励模型"自信地补全"**，而非"承认不知道"。

#### 对齐阶段（RLHF）的副作用
- 人类标注者倾向于给**详细、自信、完整**的回答打高分
- 结果：模型学会了"讨好式回答"，即使不确定也要给出看似完整的答案
- 这就是所谓的 **"谄媚（Sycophancy）"** 与过度自信

---

### 4. 上下文与注意力的限制

- **长上下文丢失**："Lost in the Middle" 现象——模型对长文本中间部分的信息利用率低
- **上下文窗口溢出**：超出窗口的信息被截断，模型"看不到"却依然作答
- **注意力稀释**：信息过多时，关键信息被淹没

---

### 5. 采样随机性

```python
temperature = 0.9   # 高温度 → 更多随机性 → 更容易偏离事实
temperature = 0.0   # 贪婪解码 → 更稳定，但仍不保证正确
```

生成时的随机采样，本身就可能选中低概率但错误的 token。

## 三、模型的能力边界（Capability Boundary）

理解边界，才知道 Agent 该在哪里"兜底"。

### 1. 知识边界
- ❌ 训练截止后的新事件
- ❌ 私有/内部数据（企业文档、个人信息）
- ❌ 长尾冷门知识

### 2. 推理边界
- ❌ 复杂多步数学计算（容易算错）
- ❌ 精确的逻辑推理链（步数一多就崩）
- ❌ 需要外部实时状态的判断

### 3. 感知边界
- ❌ 无法真正"执行"动作，只能生成文本
- ❌ 对时间、空间的物理常识理解有限

## 四、对 Agent 开发的实战启示

这才是面试中真正想听到的——**知道成因后，工程上怎么办？**

| 幻觉成因 | 对应的工程解法 |
|---------|--------------|
| 知识截止 / 私有数据 | **RAG** 检索增强，把事实喂给模型 |
| 概率预测本质 | **Function Calling** 把计算/查询交给可靠工具 |
| 过度自信 | 引导模型输出**置信度**，或"不知道就说不知道" |
| 多步推理易错 | **ReAct / CoT**，让推理显式化、可验证 |
| 结果不可信 | **Reflection 自检** + 引用溯源（Citation） |
| 忠实性幻觉 | 强约束 Prompt + 输出后校验（是否超出上下文） |

### 关键设计原则

```
不要让模型"记忆"事实 → 让它"检索"事实
不要让模型"计算" → 让它"调用工具"
不要相信模型的自信 → 建立外部验证机制
```

---

## 五、一个高频面试追问

> **"RAG 能完全解决幻觉吗？"**

**标准答案：不能。** RAG 只能缓解**知识类幻觉**，但会引入新问题：

- 检索到**错误/无关文档** → 模型照样被误导
- 检索内容正确，但模型**理解偏差**或**强行编造** → 忠实性幻觉依然存在
- 因此 RAG 之后仍需 **Rerank + 溯源 + 结果校验**

能答出这一层，说明候选人对幻觉有**系统性认知**，而非停留在"用 RAG 就行"的表面。

## 总结一句话

> **幻觉不是 Bug，而是 LLM 概率生成本质的必然产物。** Agent 工程师的核心价值，就是通过 RAG、工具调用、验证机制等手段，把这个"不可靠的概率机器"包装成"可靠的系统"。

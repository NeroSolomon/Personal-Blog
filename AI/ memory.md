# Memory 系统方案

## 概括

这是一个**为 AI助手添加长期记忆能力**的方案——让 AI 能"记住"用户之前聊过什么，下次对话时自动召回相关上下文，实现跨会话的个性化体验。

---

## 整体架构：三层洋葱模型

```
用户对话
   │
   ▼
┌──────────────────────────┐
│  Layer 1: 本地插件        │  ← 数据采集 + 注入点
│  (memory.ts)             │
└──────────┬───────────────┘
           │
           ▼
┌──────────────────────────┐
│  中间层: Next.js Proxy    │  ← 访问控制 + 灰度
│  (memory-gate.ts)        │
└──────────┬───────────────┘
           │
           ▼
┌──────────────────────────┐
│  Layer 2: 远程记忆服务     │  ← 存储 + 向量检索 + 记忆归纳
│  (test-agent-memory)     │
└──────────────────────────┘
```

---

## 各层详解

### Layer 1：本地插件 `memory.ts` — "眼睛和嘴巴"

**核心职责**：采集对话数据 → 写入远端；检索记忆 → 注入给 LLM。

#### 两条数据通路

| 通路 | 方向 | 时机 | 作用 |
|------|------|------|------|
| **写入** | 本地 → 远端 | 每次 LLM 调用前 | 把最新的"用户问题 + AI回答"对发送到远端存储 |
| **读取** | 远端 → 本地 | 每次 LLM 调用前 | 用当前用户问题做语义搜索，把相关历史记忆注入 system prompt |

#### 三个 Hook 的精妙编排

```
时间线 →

用户发消息                    LLM 开始推理                    会话压缩
    │                              │                              │
    ▼                              ▼                              ▼
┌──────────┐              ┌─────────────────┐            ┌──────────────┐
│ Hook 1   │              │ Hook 2          │            │ Hook 3       │
│ chat.    │              │ chat.system.    │            │ session.     │
│ message  │              │ transform       │            │ compacting   │
├──────────┤              ├─────────────────┤            ├──────────────┤
│ 捕获用户 │              │ ① 取最新对话对  │            │ 最后一次flush│
│ 输入文本 │              │ ② 缓冲→flush写入│            │ 保护memory   │
│ (去噪)   │              │ ③ 语义搜索      │            │ 不被压缩丢弃 │
│          │              │ ④ 注入system    │            │              │
└──────────┘              └─────────────────┘            └──────────────┘
```

**关键设计决策解读**：

1. **Fire-and-forget 写入**：`addMemoryAsync()` 不 await，写入失败也不影响用户。这是**可用性优先于一致性**的选择——宁可丢一条记忆，也不能让对话卡顿。

2. **FLUSH_THRESHOLD = 1**：缓冲 1 对就写入，几乎实时。说明团队判断**记忆的时效性比批量效率更重要**。

3. **MIN_CONTENT_LENGTH = 100**：AI 回复低于 100 字符不存。过滤掉"好的"、"明白了"这类无信息量的回复，避免垃圾记忆污染。

4. **搜索缓存 15s TTL**：同一个问题 15 秒内不重复搜索。这是应对用户快速连续发消息（如打字修正）的优化。

#### 注入格式

```xml
<memory>
以下是关于当前用户的历史记忆，可作为参考上下文：

- 用户偏好使用 TypeScript 开发
- 用户的项目使用 monorepo 架构，pnpm workspace
- 上次讨论了 Redis 缓存穿透的解决方案
</memory>
```

注入到 system prompt 中，受 **2000 token** 限制。这个上限的选择意味着大约能注入 **10-20 条记忆**，在"信息量"和"不挤占正常上下文窗口"之间取平衡。

#### 去重机制

```
user_content + "\n---\n" + assistant_content
                    │
                    ▼
              djb2 哈希算法
                    │
                    ▼
         submittedHashes Map (最多200条)
                    │
              超200条时
                    │
                    ▼
            LRU 淘汰一半 (100条)
```

**为什么不用 SHA256？** djb2 是极轻量的哈希，适合高频调用场景。碰撞概率虽高于密码学哈希，但在这个场景下"偶尔重复写入一条"的代价远低于"每次都算 SHA256"的开销。这是工程上的务实选择。

### 中间层：Next.js Proxy — "安全阀和开关"

这一层**不做业务逻辑**，只做两件事：

#### 1. 路由转发

```
客户端请求                    上游服务
/api/memory/add     →→→    /api/memories    (POST)
/api/memory/search  →→→    /api/search      (POST)
/api/memory/list    →→→    /api/memories    (GET)
```

#### 2. Gate 控制（灰度发布的精髓）

```
          ┌─────────────────────────────────┐
          │         memory-gate.ts          │
          │                                 │
          │   读(search/list)  写(add)      │
          │      独立控制       独立控制      │
          │                                 │
          │   ┌─────┐  ┌──────────┐  ┌───┐ │
          │   │ off │  │grayscale │  │ on│ │
          │   └─────┘  └──────────┘  └───┘ │
          │    全关      白名单       全开   │
          └─────────────────────────────────┘
                          │
                   MongoDB 存储
                ┌──────────────────┐
                │ memory_config    │ → {read_mode, write_mode}
                │ memory_whitelist │ → {user_id, read, write}
                └──────────────────┘
```

**读写独立控制的意义**：

| 场景 | 读 | 写 | 效果 |
|------|----|----|------|
| 全新上线 | off | off | 完全关闭，零风险 |
| 数据积累期 | off | grayscale | 白名单用户默默写入，但不使用记忆，先积累数据观察质量 |
| 小范围验证 | grayscale | grayscale | 白名单用户完整体验，收集反馈 |
| 全量发布 | on | on | 所有用户都能用 |
| 紧急回滚 | off | off | 一键关闭，不需要发版 |

**静默降级**是最精妙的设计：Gate 拒绝时不返回错误，而是返回"空成功"：
- `add` → `{success: true}`（假装写入成功了）
- `search/list` → `{results: []}`（假装没搜到记忆）

这意味着 **Layer 1 的 memory.ts 完全不需要知道 Gate 的存在**，代码零修改即可适配灰度。

### Layer 2：远程记忆服务 — "大脑"

| API | 功能 | 关键参数 |
|-----|------|----------|
| `POST /api/memories` | 写入记忆 | `infer: true` — 自动归纳 |
| `POST /api/search` | 语义搜索 | `query` + `user_id` + `limit` |
| `GET /api/memories` | 列出全部 | `user_id` |

**`infer: true` 是核心亮点**：

```
原始对话:
  User: "我在用 Next.js 14 做一个电商项目，部署在 Vercel 上，
         数据库用的 PlanetScale，现在遇到了 Server Component 
         中获取数据的 N+1 问题..."
  Assistant: "建议使用 DataLoader 模式... [500字解答]"

                    │ infer=true
                    ▼

归纳后的记忆:
  "用户使用 Next.js 14 + Vercel + PlanetScale 技术栈开发电商项目"
  "用户关注 Server Component 数据获取性能优化"
```

不存原文，存归纳后的记忆点。优势：
- **节省存储和检索 token**
- **提高搜索精度**（归纳后的语义更集中）
- **隐私友好**（不保留完整对话）

## 完整数据流走读

以一次典型的用户对话为例：

```
时间点 T1: 用户发送消息 "帮我写一个 Redis 连接池"
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

① Hook chat.message 触发
   → lastUserMessage = "帮我写一个 Redis 连接池"

② Hook chat.system.transform 触发（LLM 调用前）
   
   ② -a 写入流程:
   → 从 OpenCode API 取最新的 user+assistant 对（上一轮对话）
   → 检查 assistant 长度 ≥ 100? 
   → djb2 哈希去重
   → fire-and-forget POST /api/memory/add
     → Next.js Proxy → Gate 检查 → 转发到远端
     → 远端 infer=true 自动归纳并存储
   
   ② -b 读取流程:
   → 检查搜索缓存（15s 内同 query 命中?）
   → POST /api/memory/search { query: "帮我写一个 Redis 连接池" }
     → Next.js Proxy → Gate 检查 → 转发到远端
     → 远端做向量语义搜索，返回 top-10 相关记忆
   → 格式化为 <memory>...</memory>
   → 注入 system prompt（≤ 2000 tokens）

③ LLM 开始推理（带着记忆上下文）
   → system prompt 中包含:
     "用户偏好使用 Go 语言"
     "用户的项目使用 Redis 做缓存层"
     "之前讨论过 Redis Sentinel 高可用方案"
   → LLM 生成的回答会更贴合用户背景

④ AI 回复完成，进入下一轮等待
```

## 设计亮点总结

| 设计决策 | 权衡 | 理由 |
|----------|------|------|
| Fire-and-forget 写入 | 可靠性 ↓ 延迟 ↑↑ | 对话体验不能被记忆写入阻塞 |
| infer=true 归纳 | 信息量 ↓ 精度 ↑ | 记忆要高信噪比，不是存聊天记录 |
| 静默降级 | 可观测性 ↓ 稳定性 ↑ | 记忆是增强特性，不是核心功能 |
| 读写独立 Gate | 复杂度 ↑ 灵活度 ↑ | 支持"先存后用"的渐进式上线 |
| 15s 搜索缓存 | 实时性 ↓ 性能 ↑ | 短时间内用户意图不会剧变 |
| djb2 轻量哈希 | 碰撞率 ↑ 性能 ↑ | 场景容忍偶尔重复，不容忍延迟 |

---

## 潜在风险与改进方向

1. **记忆质量**：`infer=true` 的归纳质量完全依赖远端服务的 LLM 能力，如果归纳不准确会引入噪音甚至错误记忆
2. **记忆过时**：没有看到 TTL 或记忆衰减机制——用户半年前用 Vue、现在用 React，旧记忆可能误导
3. **记忆冲突**：如果用户信息发生变化（换公司、换技术栈），新旧记忆可能矛盾
4. **单点依赖**：远端服务 `test-agent-memory.netease.com` 如果响应慢（< 8s timeout），每次对话都要等搜索
5. **隐私审计**：记忆中可能包含敏感代码或商业信息，需要考虑数据合规和用户删除权

---

## 一句话评价

> 这是一个**工程成熟度很高**的长期记忆方案——不追求技术上的花哨，而是在每个环节都做了**面向失败的设计**（fire-and-forget、静默降级、灰度 Gate），体现了"记忆是锦上添花，不能成为系统负担"的务实哲学。
